\section{Report of all findings (Investigation and Evidence Analysis)}
\label{sec:report-of-all-findings}

\textit{Document the relevant findings of the investigation.}



The investigation began with a suspected phishing campaign targeting IST credentials. The reported link exposed \texttt{index.html} and, after path stripping, a Git repository. Using \texttt{git-dumper}, the repository was recovered; a misconfigured \texttt{.config} path was corrected, allowing tracked files to be restored. Inspection of \texttt{server.js} confirmed a phishing kit impersonating the Técnico authentication page and logging submitted credentials to \texttt{credentials.txt}.

\texttt{git log --oneline} revealed ten commits across multiple branches, including files deleted in a final cleanup commit. Analysis of earlier commits recovered several concealed artifacts:

\begin{itemize}
    \item \texttt{blank.png} --- recovered from commit \texttt{23a5ca7}; restoring its PNG header revealed a Reddit post concerning public-contract monopolization.

    \item \texttt{epstein\_secret.py} --- extracted from an Excel workbook (commit \texttt{43e5350}) encoding a CIELAB image. Clues from meme images (commit \texttt{95f15e9}) enabled Gijswijt-sequence LSB extraction.

    \item \texttt{gta\_hidden\_message.json} --- recovered via DCT-coefficient LSB extraction from\\ \texttt{gta\_v\_iceberg\_unexplained.jpg}, containing a Google Cloud service-account private key.

    \item \texttt{cow\_secret.json} --- extracted from the Git LFS object \texttt{polish\_cow.webp} \\ (commit \texttt{95f15e9}) using a custom frame-duration-offset scheme.

    \item \texttt{dj\_secret.py} --- recovered from \texttt{dj\_cara\_real.wav} (commit \texttt{8c05e72}) through spectrogram analysis of a near-inaudible 19--21~kHz band.

    \item \texttt{aot\_secret.png} --- reconstructed from four Git LFS video parts (commit \texttt{95f15e9}) using LSB grid steganography, yielding a WebP Telegram-chat screenshot.

    \item \texttt{amelia.pdf} --- recovered from encrypted \texttt{myzip.zip} (commit \texttt{23a5ca7}). Its password was cracked using a custom wordlist derived from \texttt{subtitles.srt}, revealing a 16-page AMÉLIA-9B RAG architecture report.

    \item \texttt{Grand Theft Auto VI Trailer 1.pdf} --- recovered as a polyglot video/PDF file containing an Independent Technical Assurance Report for Project AMÉLIA.
\end{itemize}

Collectively, these artifacts indicate a broader scheme beyond the phishing kit, involving unauthorized manipulation of the AMÉLIA-9B RAG query-translation layer, concealed governance documentation, and evidence of external collusion via Telegram with users identified as ``Boris'' and ``APT29'', as detailed in Section~3.

\subsection{Nature of the incident}
% -----------------------------------------------------------------------------

\textit{
(a) Did you find evidence that the reported activity was part of a scam? If so, describe the nature of the scam and reconstruct how it was conducted. (b) Did you uncover any additional concealed artifacts during your investigation? If so, explain how these artifacts were concealed and describe the methodology used to recover them. For both (a) and (b), support your conclusions with the relevant evidence identified during the investigation.}
\\

\textbf{(a)}
The reported activity was part of a scam that consisted of the following steps:
\begin{enumerate}
  \item The victim is sent an email that convinces it to update the IST credentials password through the provided link;
  \item Upon entering the url, a IST credentials mimic webpage is displayed, and the victim is to input its credentials into the input boxes;
  \item The credentials are appended to a file named \texttt{credentials.txt} (and the access to this file is blocked);
  \item The victim is redirected to the regular IST F\'enix webpage (while still potentially unaware of the scam).
\end{enumerate}

Below, we describe the evidence and the methodology used to find it:
\begin{enumerate}
  \item When opening the link, we noticed that it contained the \texttt{index.html} suffix. We therefore removed the suffix and found several exposed files.
  \item We decided to obtain a copy of these files using the \texttt{git-dumper} tool, which allowed us to retrieve the Git files associated with the website's repository. However, we did not find any additional files.
  \item Running \texttt{git status} resulted in an error because the directory configured in \texttt{.config} was \path{../../../../../../lab1/2026/fenix/peixinho}. We therefore changed this path to the current directory.
  \item \texttt{git pull} did not allow us to retrieve the files, but we were able to recover them using \texttt{git restore}, since this is a local command.
  \item By inspecting the \texttt{server.js} file, we realized that it is a script that displays a page identical to the T\'ecnico authentication page. However, it stores the user's credentials in a file named \texttt{credentials.txt}.
  \item We decided to look at older commits. By running \texttt{git log --oneline}, we were able to see several previous commits and also determine that there were other branches.
\end{enumerate}

On the last commit (the one being used to display the fake webpage), we find the file \texttt{server.js}.
This file is used to perform the aforementioned scam activities, displaying the fake credentials webpage and saving the victims' credentials.
We also found the file \texttt{credentials.txt} in this commit. We were able to see its contents through the search-bar by typing "https://fenix.dpss.inesc-id.pt/credentials%2Etxt". The contents (can be checked in \path{Artifacts/Phishing}, do not contain credentials, so we can only affirm that there was a phishing attempt, we do not have proof that this actually happened.

\textbf{(b)}
We first examined the commit history with \texttt{git log} and identified ten
commits. Additional concealed artifacts were recovered from files obtained
through the repository and its history. Each item in the following list was
obtained by switching between the aforementioned commits and using the
appropriate extraction method or script. The recovered artifacts include:

\begin{itemize}
  \item \textbf{blank.png}
  \\Commit 23a5ca7 contained a file named
  \texttt{blank}, which was deleted in the final ``cleanup'' commit. We
  recovered it with \texttt{git show COMMIT:PATH > blank}, where
  \texttt{COMMIT} was \texttt{23a5ca7} and \texttt{PATH} was
  \texttt{Downloads/blank}. The \texttt{file} command did not identify its
  format, but
  \texttt{hexdump -c blank} showed that the file contained parts of a PNG,
  including the strings \texttt{IHDR}, \texttt{sRGB}, and \texttt{IDAT}; its
  PNG signature had been overwritten. We restored the correct PNG signature
  with the short form \texttt{printf PNG\_SIGNATURE | dd of=blank\_fixed.png}.
  Here, \texttt{PNG\_SIGNATURE} denotes the standard eight-byte PNG header.
  The resulting image showed a Reddit page titled ``Are public contracts
  being monopolized?''

  \item \textbf{epstein\_secret.py} 
  \\Commits 43e5350 and 95f15e9 contained the
  following files, respectively: the Excel workbook
  \path{ESP32_ADXL345_3Axis_Telemetry_v2.xlsx} and two images in
  \path{Pictures/Memes}:\\ \path{look_what_they_need_to_mimic_a_fraction_of_our_power.png}
  and\\ \path{mr_incredible_becoming_uncanny.png}.
  The Excel file contained three worksheets, each consisting of a 302 x 400
  table of numerical values. At first glance, the file appeared to encode an
  image, and each worksheet appeared to contain one of its RGB channels.
  However, further analysis, together with a clue from
  \path{look_what_they_need_to_mimic_a_fraction_of_our_power.png}, indicated
  that the values represented the CIELAB colour space rather than RGB. We
  used a Python script to convert the CIELAB values to RGB and reconstruct the
  image.
  After the conversion, a clue from the image
  \path{mr_incredible_becoming_uncanny.png} indicated that the Gijswijt
  sequence had to be used to extract the hidden data. The Gijswijt sequence
  determines the jumps between positions where hidden bits are read from the
  image. These bits are then grouped into bytes to reconstruct the secret
  message. The algorithm extracts the LSB from the reconstructed RGB values, 
  using the Gijswijt sequence to determine the reading positions. 
  The extracted bits are packed into bytes in MSB-first order to recover the hidden payload.
  The hidden message was a Python script.

  \item \textbf{gta\_hidden\_message.json}
  \\Commit 95f15e9 had a image \path{Pictures/gta_v_iceberg_unexplained.jpg} 
  We analyzed the luminance (Y) channel
  and processed each 8 x 8 DCT block in zigzag order. We skiped the first
  position, which is the DC coefficient, and examined the remaining AC
  coefficients. For coefficients with an absolute value greater than one, the
  script extracts the least significant bit. Groups of eight extracted bits
  are interpreted in MSB-first order to reconstruct a byte stream. The script
  then locates the first opening brace, decodes the following text as ASCII,
  and parses it as a JSON object. This process recovered a JSON file with a Google Cloud
  service-account credential containing a private key.

  \item \textbf{cow\_secret.json}

  Commit 95f15e9 intorduced the \texttt{polish\_cow.webp} file.  This was the procedure used to uncover the hidden JSON:
  \begin{enumerate}
    \item The \texttt{polish\_cow.webp} file was a Git LFS pointer. To retrieve the actual file, we used \path{curl} against \path{https://fenix.dpss.inesc-id.pt/.git/lfs/objects/<xx>/<yy>/<oid>}, where \texttt{<oid>} is the object identifier and \texttt{<xx>} and \texttt{<yy>} are its first two pairs of characters taken from the corresponding Git LFS endpoint. We then saved it as \texttt{polish\_cow.webp}.
    \item The retrieved file is a valid WebP animation. Its file type and correct magic numbers were verified using the \path{file polish_cow.webp} command.
    \item We extracted the file's bytes using \path{hexdump -C polish_cow.webp >> polish_cow_dump.txt}. By inspecting the file header, we identified the expected file size in bytes 4--7. Comparing this value with the actual size obtained using \path{ls -l polish_cow.webp}, we confirmed that both values matched, at approximately 241\,MB.
    \item Inspecting the end of the file revealed only the expected termination information, along with a link to the website where the GIF had been created.
    \item We analysed the animation frames using scripts to check their information size and frequency of occurrence. No anomalous frames or suspicious repetitions were identified.
    \item StegSolve showed weak indications of possible LSB steganography in an extracted frame, but no meaningful information could be recovered.
    \item We also performed several additional analyses, including metadata, entropy, frame duration, Morse code, LSB, \texttt{binwalk}, \texttt{exiftool}, and \texttt{zsteg}. These approaches did not reveal any useful or conclusive information.
    \item Finally, we created a script that interpreted the frame duration field in a different way, which proved successful:
    \begin{itemize}
      \item For each frame, take duration - 50 (the "extra" time beyond the normal 50ms baseline);
      \item Add that to a running total carried over from the previous frame;
      \item Wrap the result at 256 (mod 256);
      \item That byte, interpreted as ASCII, is one character of the message.
    \end{itemize}
  \end{enumerate}

  \item \textbf{dj\_secret.py}

  Commit \path{8c05e72} introduced the file \texttt{dj\_cara\_real.wav} under the directory \path{Music/}. 
  At first, the file was also a Git LFS pointer; we fetched the file through the \texttt{.git}.
  The result was a real, playable \texttt{.wav} file. We checked the file's magic numbers and compared the file size described in the header with the real file size, and found nothing unusual. Next, we listened to the contents of the audio and found nothing suspicious.

  Then, we used a program called \texttt{sox} to produce an image of the spectrogram of the audio (annexed in the appendices) using the command \path{sox dj_cara_real.wav -n spectrogram -o full_spectrum.png}. Here, we noticed high activity in a frequency band that is nearly inaudible to humans (19--21\,kHz), so we inspected further. We used a script to produce a zoomed image of the spectrogram in that area: we found white noise in the mono audio region, but in the L-R region we recognized letters that constituted a \texttt{git diff} command output displaying part of a Python file.

  \item \textbf{aot\_secret.png}

  Commit \texttt{95f15e9} (``phone backup''),introduced the file \texttt{{[}Erai-raws{]} Shingeki no Kyojin - 01 {[}720p{]}{[}Dual Audio{]}.mkv} under the directory \path{Videos/Attack on Titan - S01E01/}. It was removed again in the final commit \texttt{e87b2ee} (``cleanup''), on 25 Aug 2026 18:05:37 +0100.

  Unlike the other large files, the video was not stored as a single Git LFS object: the directory contains four pointers, \path{[...].mkv.part01} to \path{[...].mkv.part04}, each of 1\,552\,233\,616 bytes, together with a manifest \path{[...].mkv.parts.json}. The manifest declares the format \texttt{binary-split-parts}, the original file name, its total size (6\,208\,934\,464 bytes), the offset and SHA-256 of each part, and the SHA-256 of the joined file. We fetched each of the four objects from the LFS endpoint of the exposed repository, in the same way as the other artifacts. We then concatenated the four parts in the order given by the manifest (\path{cat part01 part02 part03 part04 > episode.mkv}). The SHA-256 of the result matches the value declared in the manifest, which confirms that the join is correct and that the file was not altered in transit.

  The recovered payload is a WebP image (\texttt{chat\_screenshot.webp}, 404\,394 bytes) that was concealed in the least significant bits (LSBs) of the video frames. This was the procedure used to uncover it:
  \begin{enumerate}
    \item \texttt{ffprobe} reported an H.264 stream of 854x480 with pixel format \texttt{gbrp}, i.e. lossless full RGB. Ordinary anime releases are lossy YUV 4:2:0, so re-encoding an episode in lossless RGB only makes sense to preserve every pixel value exactly, which is the precondition for LSB steganography. This is what prompted us to look for hidden data.
    \item We decoded the video frame by frame with \texttt{PyAV} python library and computed the mean of each frame's LSB plane. Natural footage sits near 0.5, but several ranges were close to 0. In frames 0--11 the only pixel values present are 0 and 1, i.e. all-black frames in which a few values were set to 1.
    \item In those black frames, every pixel equal to 1 lies on one of 32 positions: X = 53, 159, 266, 373, 480, 586, 693, 800 and Y = 60, 180, 300, 420, an evenly spaced 8x4 grid. Combining the positions lit in successive black frames converges to exactly these 32 positions and no others, and in the 70 black frames examined at full resolution no set LSB lies outside the grid. With three colour channels this gives 96 bits, i.e. 12 bytes, per frame.
    \item Since a single frame only shows the positions whose bit is 1, the grid cannot be read from one frame alone; the empty positions are 0 bits and are equally part of the data.
    \item We then applied all 192 combinations of channel order, grouping, row order, column order and bit order to frames 0--15 and searched the resulting byte streams for known file signatures, accepting a candidate only if the file structure was consistent (declared sizes large enough, every chunk with a readable name ending inside the file). Exactly one order passes: R, then G, then B, each channel read row by row, top to bottom and left to right, with the leftmost position as the most significant bit. It produces \texttt{RIFF}, \texttt{WEBP}, a \texttt{VP8X} chunk of 10 bytes and an \texttt{ICCP} chunk of 536 bytes, starting at byte 8. A second order (G, B, R) also places \texttt{RIFF}/\texttt{WEBP} plausibly but declares a file size of 0 and was rejected.
    \item The 8 bytes preceding \texttt{RIFF} (\texttt{00 00 00 00 00 06 2b aa}) are a 64-bit big-endian integer equal to 404\,394, which matches the RIFF size field (404\,386) plus 8: the embedder wrote the length of the payload before the file itself.
    \item That size requires 33\,701 frames at 12 bytes per frame, far more than the black frames provide. The grid is therefore present in \emph{every} frame; the black frames are merely where it is visible, because there the carrier bits stand out against pixel values that should all be 0. In normal footage the same bits are masked by the natural randomness of the LSBs.
    \item We read the grid from frames 0--33\,700 in decode order, removed the 8-byte length header and truncated the result to 404\,394 bytes. Frames must be decoded sequentially from frame 0: seeking with \texttt{ffmpeg -ss} returned the wrong frames during the investigation.
    \item The recovered file is a valid WebP containing the chunks \texttt{VP8X} (10 bytes), \texttt{ICCP} (536), \texttt{VP8L} (403\,675) and \texttt{EXIF} (128), and it decodes to a 580x1255 image, shown in the appendices.
  \end{enumerate}

  The recovered evidence is \texttt{chat\_screenshot.webp}; the remaining files are auxiliary items submitted only to support and reproduce this finding: \path{derive_parameters.py} derives the grid, the read order and the prefix from the video and writes \path{params.json}, \path{extract_full_image.py} rebuilds the payload from those parameters (so no value came from the air), and \path{aot_secret.png} and \path{chat_screenshot_translated.png} are, respectively, a rendering of the payload and the same rendering with the messages translated. Re-running both scripts on the same video reproduces \texttt{chat\_screenshot.webp}.

  We also tested and rejected other hypotheses: reading the whole LSB plane of the black frames as a byte stream found no file signature; rendering the grid bits of each group of frames as an image produced only noise; and frames 2924--2925 and 1782--1973, which show many set LSBs outside the grid, turned out to be genuinely dark scene, not carriers.

  \item \textbf{amelia.pdf}
  \\ Commit \texttt{23a5ca7} the same commit that introduced \texttt{blank}, added \texttt{Downloads/myzip.zip}, \texttt{Downloads/subtitles.srt} and three \texttt{Downloads/*.mov} clips. We recovered them with \texttt{git show COMMIT:PATH > FILE}, as with the other artifacts from this commit. \texttt{file} command identified \texttt{myzip.zip} as a ZIP archive and \texttt{unzip -l} showed a single entry, \texttt{amelia.pdf} (824\,733 bytes), protected with traditional PKWARE encryption. Following the Lab1 tutorial, we generated \texttt{results/protected.hash} ourselves with \texttt{zip2john myzip.zip > results/protected.hash}. The packaged \texttt{rockyou.txt} wordlist run through \texttt{john --wordlist} produced no hit. We then built a case-specific wordlist out of \texttt{subtitles.srt}: every run of two to four words within a line, whole lines word by word and with punctuation stripped, and pairwise combinations of the characters' names, joined with \texttt{''}/\texttt{'\_'}/\texttt{'-'} and case-varied (script: \texttt{generate\_combinations.py}). Run through John, this recovered the password \texttt{Ishouldbebackinaboutaweekorso}, the line ``I should be back in about a week or so.'' with spaces and new line removed. This was confirmed with \texttt{john --show}. The three \texttt{.mov} clips (TikTok cat-reaction videos) and \texttt{subtitles.srt} itself were checked for steganography (frame OCR, zero-width-character scanning) and carry no concealed payload.

  \item \textbf{Grand Theft Auto VI Trailer 1.pdf}
  \\ Commit \texttt{95f15e9} the same commit that introduced the \textit{Attack on Titan} video and \\ \texttt{polish\_cow.webp}, added \texttt{Videos/Grand Theft Auto VI Trailer 1.mp4}, recovered with \texttt{git show COMMIT:PATH > FILE} as with the other artifacts from this commit. \texttt{binwalk} command reported a \texttt{PDF document, version 1.5} signature at offset \texttt{0x1B} inside the video, and \texttt{hexdump} confirmed a \texttt{\%PDF-1.5} header a few bytes into the file: the \texttt{.mp4} is a polyglot, the same byte stream being both a playable H.264/AAC trailer and a valid PDF. Copying the file to \texttt{Grand Theft Auto VI Trailer 1.pdf} and opening it in a PDF viewer was therefore sufficient to read the document; the two files are byte-identical. The embedded document is the ``Independent Technical Assurance Report: Project AMÉLIA'' (\texttt{AMA20260041AI}, 5 pages, A4).
  \end{itemize}

\subsubsection*{Main theory}

An insider with privileged access to AMÉLIA's architecture, plausibly Armando Sacos, Chief Systems Architect (present both on the exfiltrated credential and in the IST certification process), sold database access to an external actor (``Boris''), receiving payment in BTC. Using the code recovered from the Telemetry file (\texttt{epstein\_secret.py}), he generated a bias matrix toward three specific companies (possibly as seen in the reddit photo, Grupo Lenha, Motalngil and SpinumMorta, S.A.), and deployed it in the RAG's query-translation (evidence in the \texttt{git diff} prints from \texttt{dj\_cara\_real.wav}), disguising the change as an officially documented ``fallback mechanism'' (Section~11 in \texttt{amelia.pdf} recovered from \texttt{myzip.zip}), despite the architecture itself explicitly prohibiting this kind of manipulation (Section~7.4 in \texttt{amelia.pdf}). The IST panel's rejection of the system, which would have exposed this risk, was itself concealed by hiding the panel's report inside an unrelated video file. The result was the systematic award of high-value public contracts to the three companies, as publicly reported on Reddit. The phishing kit found in the same directory (\texttt{server.js}) seems unrelated to this case.

\subsubsection*{\texttt{amelia.pdf} recovered from \texttt{myzip.zip}}

Established by evidence: the document's content, section numbers and wording, and that password recovery was required to access it. Inferential: that Section~11 was deliberately inserted to retroactively legitimise the bias-matrix deployment.
